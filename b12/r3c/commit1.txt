fix(blocks): route() of a block layout starts from the layout; a drag follows a layout column only where that adds nothing (B12.13, fix round 1)

Lead decision of 2026-11-19 (option A) and the verifier's findings 1, 4-9
on the package's previous head:

- The second internal setting is gone (`--cfg flowmaid_route_layout`,
  `quality::with_route_from_layout`): wherever the block layout's switch
  is on, route() of a block-mode part starts from the static layout's
  drawing of it (ruling 1). One internal switch again, as spec 4.1 has it.
- scene() of a block layout hands its drawing to that memo, so the first
  route() after scene() on a thread does not lay the graph out again.
- A drag's followed path (an edge redrawn because an end moved, kept on
  the layout's columns) that adds a crossing, a crossing within its fan,
  or a node or frame its base path did not meet is drawn as the release
  before redrew it (`refuse_costly_follows`). blocks/hub5 with `invoice`
  dragged by (60, 25): `bill` no longer crosses `token -> invoice`.
- A redrawn frame keeps the layout's room only on a side where that room
  takes in no node or frame it does not hold and no path the drag draws
  afresh; elsewhere it takes its members' frame (R6). examples/advanced
  with Job Queue dragged by (-150, 80): Async Workers no longer grows
  over Redis, and the kept gateway / Redis edges cross nothing.
- A followed edge's label stays on its leg at the same share, its chip
  clear of the leg's turns (or no nearer than the base had it); every
  path a block layout's drag draws turns its corners as the router
  rounds them (a slid end leg left a rounding point 20 px off a corner);
  a node a host moves and resizes in one call carries its followed ends
  onto its new box.
- A route_partial() fallback for a whole-drawing pan goes through
  route(), which moves the layout's drawing.
