01 · Start

Overview

flowmaid is a diagram engine that speaks Mermaid syntax and is written in pure Rust with zero dependencies — no C libraries, no JavaScript runtime, nothing beyond the Rust standard library. Feed it Mermaid-like text, get back an SVG string or plain positioned geometry you can paint with any UI toolkit.

  • 12 diagram types — flowchart, ER, class, sequence, state, pie, mindmap, user journey, git graph, architecture, timeline, sankey.
  • Fast — about 113× faster than mermaid 12.2.0 (geometric mean over 25 diagrams); most hand-written diagrams render in under a millisecond. See Performance.
  • Layout from mermaid's family — a Sugiyama pipeline following dagre, the algorithm mermaid.js uses. Flowchart and state edges run on the axes with rounded corners, crossing lines hop over each other, and a hub's fan is drawn as a comb.
  • Interactive by design — a scene/route API exposes every node and edge as plain geometry, so hosts can implement drag & drop, picking and re-routing without re-running layout, then save the graph back as mermaid text.
  • Runs anywhere Rust runs — native CLI, desktop apps, or the browser through one WebAssembly file (that is what powers the playground).
  • Line-numbered errors — parse failures tell you the offending line.
02 · Start

Installation

Requires Rust 1.75 or newer. flowmaid has no other requirements.

As a library

cargo add flowmaid

or in Cargo.toml:

[dependencies]
flowmaid = "0.40"

As a command-line tool

cargo install flowmaid

This installs a flowmaid binary that converts .mmd files to SVG.

03 · Start

Quick start — CLI

# file in, file out
flowmaid diagram.mmd -o diagram.svg

# or classic UNIX pipes
cat diagram.mmd | flowmaid > diagram.svg

Try it with this diagram.mmd:

flowchart TD
    A([Start]) --> B[Read input]
    B --> C{Valid?}
    C -->|yes| D[Process data]
    C -->|no| E[Show error]
    E --> B
    D ==> F((Done))

flowmaid --help lists the options.

04 · Start

Quick start — Rust library

The one-call API renders any supported source straight to an SVG string:

fn main() {
    let svg = flowmaid::render_svg("flowchart TD\nA --> B{OK?}").unwrap();
    std::fs::write("out.svg", svg).unwrap();
}

For more control, parse first and match on the document type:

use flowmaid::{parser, model::Document};

match parser::parse_document(src) {
    Ok(Document::Flowchart(g)) | Ok(Document::State(g)) => {
        let scene = flowmaid::scene::scene(&g);   // positioned geometry
        let svg   = flowmaid::scene::to_svg(&scene);
    }
    Ok(Document::Er(d))       => { /* flowmaid::er::scene(&d) … */ }
    Ok(Document::Sequence(d)) => { /* flowmaid::seq::scene(&d) … */ }
    Ok(other)                 => { /* class, pie, mindmap, journey … */ }
    Err(e) => eprintln!("parse error: {e}"),      // line-numbered
}

Labels support Mermaid's inline markup: <br/> line breaks and <b>/<i> styling render as real bold/italic text.

Performance

25 sample diagrams — flowcharts from a handful of nodes up to 52 nodes or 75 edges, plus every other diagram type — rendered from the same .mmd source by flowmaid and by mermaid 12.2.0 (in headless Chromium).

~113×faster than mermaid, geometric mean
20 / 25diagrams under a millisecond
1.5–25×smaller SVG
~3 msa drag frame on the densest sample

Dragging a node does not re-run layout: route_partial re-routes only the edges the move can affect. The full table, the method and the machine are in the README's Benchmark section.

06 · Guides

Interactive apps (drag & drop)

Every diagram type exposes its geometry as a scene: node centres, sizes, shapes, edge paths, cluster boxes — plain data, no canvas assumed. The flow for an editor with draggable nodes:

use flowmaid::scene;

let s0 = scene::scene(&graph);                 // 1. automatic layout
let mut pos: Vec<(f64, f64)> =                 // 2. host owns positions
    s0.nodes.iter().map(|n| (n.x, n.y)).collect();

// … user drags node i, host updates pos[i] …

let s1 = scene::route_partial(                 // 3. LOCAL re-route:
    &graph, &pos, &s0, &auto_pos);             //    untouched edges keep
                                               //    engine-quality routing
let svg = scene::to_svg(&s1);                  // 4. export any state
  • scene() — full automatic layout (what the CLI and playground use).
  • route(g, &pos) — re-route every edge for arbitrary positions, without re-running layout.
  • route_partial(g, &pos, &base, &base_pos) — re-route only the edges a move can affect; the rest keep the base drawing.
  • Picking — Scene::{hit_test, node_at, edge_at, cluster_at, hits_in_rect, nearest_node} match what is painted, a crossing hop's arc included.
  • Saving — emit::to_mermaid(&graph) writes the graph back as valid mermaid text.

Other diagram types

  • ER and class diagrams have the same scene / route / to_svg triple (er::, class::); state diagrams use the flowchart API directly.
  • Mindmaps have mindmap::scene / mindmap::route.
  • Sequence, pie, journey, timeline, sankey, git graph and architecture diagrams are static: a scene() and a to_svg(), no route().
A flowchart or state edge drawn on the axes comes as SceneEdge::waypoints, which a painter's spline turns through as rounded corners. The hops at crossings are painted by flowmaid's SVG writer only; the waypoints hold the plain path.

WebAssembly

The flowmaid-web repository compiles the engine to one wasm file with small JS bindings — the playground is built on exactly this. On engine 0.40.0 that file is about 2.8 MB, about 1.1 MB with gzip.

import init, { render_svg } from "./pkg/flowmaid_web.js";

await init();
document.body.innerHTML =
    render_svg("flowchart TD\nA([Start]) --> B{OK?}");

Building the bundle yourself

git clone https://github.com/go-routine-id/flowmaid-web
cd flowmaid-web
wasm-pack build --target web --release   # emits pkg/
python3 -m http.server                   # open http://localhost:8000

09 · Guides

Advance swimlanes (JSON input)

Besides the mermaid-syntax diagram types, the engine ships an engine-native swimlane renderer driven by JSON: vertical lane columns, top-down nodes, orthogonal edge routing, and drag-friendly re-renders with caller-controlled lane widths. Shapes reuse the flowchart vocabulary (rect, rounded, stadium, diamond, circle, cylinder, …). Entry points:

let svg   = advance::render_advance_svg(json)?;                // JSON -> SVG
let scene = advance::layout_advance(json)?;                    // JSON -> geometry
let svg   = advance::render_advance_routed(json, &positions)?; // after drag

render_advance_routed_with_lanes additionally takes caller-controlled lane widths, margin, and gap — the engine side of resizable swimlane columns. Content dragged outside the canvas is translated back into view.

The same engine also reads a concise text DSL — nested lanes, styling, and ports:

let svg = advance::render_advance_text_svg(src)?;   // text DSL -> SVG
classDef primary fill:#e8f0fe,stroke:#4285f4
config margin 24
lane backend "Backend" {
  a[Auth]::primary
  b[API Gateway]
  a --> b
}
lane web "Web" {
  c{Check}
  c --> b:top        # ported edge — enter b through its top
}
style a-->b color:#188038,dash:4 2
style c fill:#fff8e1
  • Nested lanes — lane id "Title" { ... } opens a child scope; a standalone } closes it.
  • Styling — Mermaid-style classDef/class/ a::name/style directives; style a-->b … targets an edge. Node keys fill/stroke/ stroke-width/color; edge keys add dash and label-fill.
  • Ports — a:right --> b:top pins the anchor sides (left/right/top/bottom/auto).
  • <br/> — line breaks in node labels, edge labels, and lane titles.

AdvanceScene also exposes drag-and-drop picking — hit_test, node_at, edge_at, lane_at, nearest_node.

This diagram kind has no mermaid header, so it stays outside the type counts above — they refer to mermaid-syntax types only.

How layout works

Flowcharts (and state, class and ER diagrams, which map onto the same graph) go through a Sugiyama pipeline following dagre — the algorithm family mermaid.js uses:

  1. DFS marks back-edges so cycles cannot break the layering.
  2. Longest-path layering assigns nodes to ranks.
  3. Long edges split into per-rank dummy chains that reserve routing channels; a labelled edge sizes a dummy to its label so labels claim real space.
  4. Ordering cuts crossings with weighted-median sweeps plus an adjacent-swap transpose, keeping the best round. Subgraph members stay contiguous, bracketed by invisible border walls.
  5. Brandes-Köpf coordinate assignment straightens long edges and centres fan-in/outs. All four directions are one transform at the end.
  6. The scene finishes every edge in the same fixed stages in scene(), route() and route_partial(): distinct, ordered ports on every node side, edges redrawn on the axes with rounded corners, repair of edges that pass through a node or a foreign frame or run on top of another edge, combed fans, and collision-aware label placement.

The SVG writer then paints the scene, adding a small hop where a level stretch of one edge crosses a plumb stretch of another. Sequence, pie, journey, timeline, sankey, git graph, mindmap, architecture and swimlane diagrams use their own dedicated layouts.
